# Marketplace Backend

Учебный backend маркетплейса на Python.

API позволяет зарегистрироваться, просматривать каталог, создавать заказы, оплачивать и отменять их. Клиент передаёт список товаров и их количество непосредственно при создании заказа. Оплата учебная — эндпоинт меняет статус заказа без обращения к платёжному провайдеру.

## Возможности

- Регистрация и вход, JWT в HttpOnly cookie, хеширование паролей с Argon2.
- Роли пользователя и администратора.
- Создание товаров и категорий администратором, публичный просмотр каталога с пагинацией.
- Создание заказа с проверкой наличия товаров и списанием остатков.
- Сохранение цены каждой позиции на момент покупки и расчёт суммы через `Decimal`.
- Просмотр собственных заказов; администратор может просматривать все заказы.
- Оплата, отмена с возвратом остатков и завершение заказа администратором.
- Транзакции и блокировки PostgreSQL для защиты от конкурентного списания и конфликтующих изменений статуса.

## Стек

Python 3.14+, FastAPI, Pydantic, SQLAlchemy 2.x с async ORM, asyncpg, PostgreSQL 17, Alembic, python-jose, pwdlib, pytest, pytest-asyncio и HTTPX.

## Локальный запуск

Нужны Python 3.14+, Docker и Docker Compose. Команды ниже рассчитаны на Bash и выполняются из корня репозитория. PostgreSQL запускается в контейнере, приложение — локально.

### 1. Установка зависимостей

```bash
python3.14 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Полный список зависимостей приложения и тестов находится в `requirements.txt`.

### 2. Настройки

Создайте файл `.env` в корне проекта:

```dotenv
DB_HOST=localhost
DB_PORT=5433
DB_USERNAME=postgres
DB_PASSWORD=replace-with-local-password
DB_NAME=postgres

SECRET_KEY=replace-with-generated-secret
ALGORITHM=HS256
EXPIRES_IN_DAYS=30
```

Задайте свой `DB_PASSWORD`. Для `SECRET_KEY` сгенерируйте значение и вставьте его вместо заглушки:

```bash
python -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Настройки читаются из `.env` через `pydantic-settings`; переменные окружения имеют приоритет. Файл `.env` исключён из Git.

### 3. База данных и миграции

```bash
docker compose up -d db
docker compose exec db sh -c 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Дождитесь ответа `accepting connections`, затем примените миграции:

```bash
python -m alembic upgrade head
```

В `docker-compose.yml` порт PostgreSQL проброшен как `5433:5432`, поэтому для локального приложения нужен `DB_PORT=5433`. Данные сохраняются в Docker volume `pgdata`. Переменные `POSTGRES_*` создают пользователя и базу при первой инициализации пустого volume; изменение `.env` не переименовывает уже созданную базу и не меняет её пароль.

### 4. Запуск API

```bash
python -m uvicorn app.main:app --reload
```

- API: <http://127.0.0.1:8000>
- Swagger UI: <http://127.0.0.1:8000/docs>
- ReDoc: <http://127.0.0.1:8000/redoc>
- OpenAPI: <http://127.0.0.1:8000/openapi.json>

## Работа с API

В Swagger UI выполните `POST /user/register`, затем `POST /user/login`. Вход принимает JSON с `login` и `password` и устанавливает cookie `token`. Браузер отправляет её в следующих запросах к этому же адресу. `POST /user/logout` удаляет cookie.

JWT содержит ID пользователя в `sub` и срок действия в `exp`. При авторизации проверяются подпись, срок действия и наличие пользователя в БД. Refresh-токены не реализованы; после истечения JWT нужно войти заново. Выход удаляет cookie клиента, но не отзывает уже выданный токен на сервере.

### Права администратора

Новые пользователи создаются без административных прав. Для локальной проверки зарегистрируйте пользователя, например с логином `demo`, и откройте PostgreSQL:

```bash
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Выполните SQL, заменив `demo` на нужный логин:

```sql
UPDATE users
SET is_admin = true
WHERE login = 'demo'
RETURNING login, is_admin;
```

Для выхода из psql введите `\q`. Новый JWT не нужен: права читаются из БД при каждом запросе. Администратор управляет данными через API; отдельного интерфейса админки нет.

### Основные эндпоинты

| Метод | Путь | Действие | Доступ |
| --- | --- | --- | --- |
| POST | `/user/register` | Регистрация | Все |
| POST | `/user/login` | Вход | Все |
| GET | `/user/me` | Текущий пользователь | Авторизованный пользователь |
| POST | `/user/logout` | Выход | Все |
| POST | `/item/create` | Создание товара | Администратор |
| GET | `/item/items` | Список товаров | Все |
| GET | `/item/{item_id}` | Товар по ID | Все |
| POST | `/item/category/create` | Создание категории | Администратор |
| GET | `/item/categories` | Список категорий | Все |
| POST | `/order/create` | Создание заказа | Авторизованный пользователь |
| GET | `/order/orders` | Свои заказы, для администратора — все | Авторизованный пользователь |
| GET | `/order/{order_id}` | Заказ по ID | Владелец или администратор |
| PATCH | `/order/{order_id}/pay` | Учебная оплата | Владелец или администратор |
| PATCH | `/order/{order_id}/cancel` | Отмена | Владелец или администратор |
| PATCH | `/order/{order_id}/complete` | Завершение | Администратор |

Списки товаров, категорий и заказов принимают `page` (от 1, по умолчанию 1) и `limit` (от 1 до 20, по умолчанию 5). Например: `/item/items?page=2&limit=10`. Ответ — JSON-массив, без общего количества записей.

### Создание заказа

Тело запроса `POST /order/create`:

```json
{
  "items": [
    {
      "item_id": "123e4567-e89b-42d3-a456-426614174000",
      "quantity": 2
    }
  ]
}
```

Замените `item_id` на ID существующего товара. Список должен содержать хотя бы одну позицию; количество — положительное целое число. Повторять один товар в списке нельзя. Цены и итоговую сумму рассчитывает сервер.

### Жизненный цикл заказа

| Операция | Переход | Остатки |
| --- | --- | --- |
| Создание | → `created` | Списываются |
| Оплата | `created` → `paid` | Не меняются |
| Завершение | `paid` → `completed` | Не меняются |
| Отмена | `created` → `cancelled` | Возвращаются |

Повторная оплата заказа в статусе `paid` и повторное завершение в статусе `completed` возвращают текущий заказ. Повторная отмена и недопустимые переходы возвращают `409`. Автоматической отмены неоплаченных заказов по таймеру нет.

Списание выполняется условным `UPDATE` с проверкой `stock >= quantity`. Создание заказа, его позиций и изменение остатков проходят в одной транзакции. Если одного из товаров не хватает, изменения откатываются. Для оплаты, отмены и завершения строка заказа блокируется через `SELECT ... FOR UPDATE`. При обработке нескольких товаров используется порядок по UUID.

## Тесты

Тесты отправляют запросы через HTTPX `ASGITransport` прямо в приложение, используя настоящую PostgreSQL. Отдельно запускать Uvicorn для них не нужно.

### Подготовка тестовой базы

После запуска PostgreSQL создайте отдельную базу `test` один раз:

```bash
docker compose exec db sh -c 'createdb -U "$POSTGRES_USER" test'
DB_NAME=test python -m alembic upgrade head
```

Если база уже существует, достаточно применить миграции. `DB_NAME=test` в этой команде меняет настройку только на время запуска Alembic; редактировать `.env` не нужно.

Фикстуры используют настройки подключения из `.env`, заменяя имя базы на `test`. Перед каждым тестом таблицы этой базы очищаются через `TRUNCATE`. Используйте её только для тестовых данных и запускайте набор последовательно: параллельные процессы pytest с одной базой будут мешать друг другу. Конкурентные запросы внутри отдельных тестов запускаются самим тестом.

### Команды

```bash
python -m pytest tests -q
```

Отдельный файл и конкурентные сценарии:

```bash
python -m pytest tests/test_orders.py -q
python -m pytest tests/test_orders.py -k concurrent -q
```

Отчёт о покрытии:

```bash
python -m pytest tests --cov=app --cov-report=term-missing
```

Набор включает проверки регистрации, JWT, прав доступа, валидации, пагинации, исторических цен, расчёта суммы, переходов статусов и отката остатков. Конкурентные сценарии проверяют покупку последней единицы товара, двойную отмену и оплату одновременно с отменой.

## Структура проекта

```text
app/
  main.py          — создание FastAPI-приложения
  core/            — настройки, пароли, JWT и исключения
  db/              — базовая ORM-модель и сессии БД
  dependencies/    — текущий пользователь и проверка прав
  models/          — ORM-модели и статусы заказов
  schemas/         — модели запросов и ответов
  routes/          — HTTP-эндпоинты
  services/        — бизнес-правила и границы транзакций
  repositories/    — запросы к БД
migrations/        — миграции Alembic
tests/             — фикстуры и тесты API
```

Запрос проходит через `routes → services → repositories → PostgreSQL`. Сервисы управляют `commit()` и `rollback()`, репозитории выполняют запросы и при необходимости `flush()`. Категории относятся к области товаров, позиции заказа — к области заказов.
